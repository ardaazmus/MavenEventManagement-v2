## 1. Executive result

The previous “development server is ready but the browser cannot reach the application” condition is resolved for this local review. The actual cause was the process boundary: a development server started inside the restricted execution sandbox was not reachable from the desktop browser. Starting the same local server as a host process bound only to `127.0.0.1` restored browser access. The old in-app browser tab continued to display its cached offline fallback; a fresh tab loaded the application. No LAN binding was used.

This proves that the current checkout can render locally and that its current SQLite connection responds. It does **not** prove that a production host, authenticated staff account, tenant isolation, migrations, or external-user permissions are correct. The live app reported `authEnabled: false`, so the inspection was the unauthenticated demo surface—not an authenticated Firma B user or an adversarial Firma B/Firma C isolation test.

The accepted target architecture remains a modular monolith with a Firma B work portfolio as the workspace entry point, a work-specific summary and second-level navigation, Firma A tenant entitlement administration, and distinct public/personal/B2B/partner experiences. The current UI still opens into an event-edition workspace with a long fixed module menu. The target architecture is therefore a planned migration, not the present product state.

## 3. Current-code findings mapped to the target architecture

Severity describes the risk to the proposed migration and current operations. These findings build on the five source-only reviews recorded in `10-INDEPENDENT-CODE-REVIEW-ADDENDUM.md`; verify the current line-level source again before implementation.

### P0 — authorization scope must be made explicit before adding Firma A grants

1. **A work-scoped admin assignment can be interpreted as broad organization administration.** The assignment route permits tenant or same-tenant edition scopes (`src/lib/users/assignments.ts:112`, `src/app/api/users/[id]/roles/route.ts:69`), while the evaluator’s role-key shortcut can grant broad access without proving assignment scope (`src/lib/api/permissions.ts:548`). The target design must not translate “work/event administrator” into Firma B tenant administrator. Invariant: tenant-owner/admin authority can only exist at tenant scope; work roles remain contained in their Work.
2. **Stored scope metadata is not yet sufficient evidence that each API evaluates scope.** `RolePermission.scopeType` is present (`prisma/schema.prisma:2578`), but the evaluator path and generic item routes need explicit tenant/work/action scope enforcement (`src/lib/api/permissions.ts:558`; `src/app/api/[entity]/[id]/route.ts:59,94`). Require authorization on list, item, search/count, exports and asynchronous jobs; an identifier or hidden menu item is not a boundary.
3. **Related-record ownership chains are not uniformly proven by schema constraints.** Independently supplied parent IDs can connect tenant/work-owned records. Examples include Order/Payment, registration/participation/entitlement claim, and FormSubmission/Form/Edition (`prisma/schema.prisma:688,824,843`). Inventory every relation, scan existing rows before backfill, and either enforce compatible composite ownership constraints or validate the complete parent chain on every write and migration.
4. **Sponsor agreement scope is narrower than some returned subresources.** The sponsor response filters agreements by token scope (`src/app/api/portal/sponsor/route.ts:56-65`), while entitlements/claims, orders/payments and staff have organization-level queries (`:67-94`). This is not evidence of Firma B/C cross-tenant leakage; it is a potential intra-tenant overexposure when a sponsor receives access to only one agreement. Build a response-field × grant-scope matrix and test agreement-level and organization-level grants separately.
5. **Approval identity and high-value payment approval need trusted actor semantics.** The flow accepts `decidedBy`/`enteredBy` from request payloads (`src/app/api/flows/route.ts:54,79,243`); the reviewed high-value manual-payment branch marks payment `SUCCEEDED` and records static `Tenant Sahibi` above the threshold (`:261-271`). Use the authenticated actor as the source of identity. Where policy requires separation of duties, keep the transaction pending until a distinct authorized reviewer decides; persist both actors and timestamps.

### P1 — data/work lifecycle and partner submissions

6. **Form review, approval decision and operational registration can be conflated.** Public registration has `autoApprove` handling and constructs registration state (`src/app/api/public-register/route.ts:120,172`; `src/lib/api/registration-chain.ts:105,119`); the form-submission review route must be checked for ordering (`src/app/api/form-submissions/[id]/route.ts:49`). Model and test three separate facts: submission review status, approval-case decision, and operational outcome/confirmation. External form/import/partner data stays a proposal until Firma B’s configured approval. Do not let a shortcut silently consume a seat, issue a badge, create a confirmed payment/accommodation, or trigger definitive communications.
7. **Capacity and partner entitlements need one idempotent reservation lifecycle.** Registration-category capacity and sponsor/partner quota are currently separate paths (`prisma/schema.prisma:510,798,824`; `src/lib/api/registration-chain.ts:105`). Specify reserve → approve → consume, and reject/cancel → release, including retries and simultaneous submissions. A single person must not consume capacity or entitlements twice.
8. **Portfolio identity and communication consent have competing representations.** Person/Organization/CustomerContact and `ContactConsent` coexist; the legacy `CustomerContact.commsOptIn` default is permissive (`prisma/schema.prisma:230,1612,1630,2727`). Canonical portfolio identity must be separated from work participation and campaign audience projections. Campaign delivery must resolve by purpose/channel consent evidence; missing legacy data must not become consent. Empty spreadsheet cells must not erase existing identity or consent.
9. **Imports need a shared evidence contract, not necessarily one shared engine.** Registration, reservation and customer-contact imports have separate preview/commit routes (`src/app/api/registrations/import/route.ts`, `/api/reservations/import`, `/api/customer-contacts/import`). Require source/hash, preview validation, row-level accepted/rejected/skipped results, submitting actor, review state, commit receipt and idempotency key for each. External rows remain pending until Firma B approves them.
10. **Firma A, Firma B and Work are not yet separate current product planes.** The current live shell is tenant/edition-oriented. The target `Tenant` can seed Firma B but does not itself provide the platform-owner plane, Firma A’s per-tenant module-entitlement decision, or the intervening Work aggregate. Do not expose code/deployment/secrets as Firma B controls; Firma A’s product operation plane owns those. Firma B must control tenant profile, staff/departments, internal roles, tenant-active modules, Work activation, and explicit external capabilities.
11. **The module catalog is duplicated and currently out of parity.** The reviewed baseline contains 27 UI registry entries and 26 API permission module IDs; `company-communications` is the identified UI-only entry (`src/lib/constants.ts:460-477`, `src/lib/module-components.tsx:31-52`, `src/lib/api/permissions.ts:19`, `src/lib/manifest/index.ts:10`). The entity manifest is not the complete product-module manifest. Establish exact UI/API/entitlement/capability parity before adding Firma A tenant grants; do not silently invent a permission for a UI-only item or remove functionality.
12. **Module composition rules are not yet enforceable end-to-end.** The visible navigation uses fixed groups (`src/lib/constants.ts:444`, `src/components/maven/shell.tsx:103-147`) and the dependency-cruiser rules currently report no violations, but the existing domain manifests/registries do not prove that module dependencies, settings, setup steps, summary contributions, external surfaces and tests are all sourced from one contract. Use a single module manifest as a lightweight modular-monolith catalog, adapt current registries incrementally, and block activation when dependencies are not met. Do not introduce a plugin marketplace or microservices as a prerequisite.

### P1 — UI, reporting and scale

13. **The first screen is an edition list, not Firma B’s work portfolio.** The live “Etkinlikler” cards contain name/date/location, status/counters, module badges and actions; they do not present the agreed client/organizer, internal accountable staff, work type/profile, last activity, next action and accessible-by-current-user context as the primary portfolio card. Source: `src/components/maven/views/editions.tsx:255` and `src/components/maven/shell.tsx:192,354-356`. Preserve this screen as a Work/edition history and transition surface; do not pretend it is already the accepted Firma B home.
14. **The shell exposes a long seven-group module list as the primary work navigation.** It has no work-specific second rail for a selected module’s subflows/wizards and no current role/department-filtered work portfolio. Source: `src/lib/constants.ts:444-496`, `src/components/maven/shell.tsx:103-147`. Implement the approved hierarchy in stages: Firma B home/settings → selected Work summary → Work-specific first-level module rail → module subflow rail, with current user scope shaping both visibility and server authorization.
15. **The dashboard contains useful grouped operational metrics but is still edition-centric.** It has grouped metrics for registration, approval, people, attendance, finance, sponsorship, scientific/program, accommodation/onsite and activity. Retain these as the selected-work summary, add explicit period/status definitions and stale-data timestamps, and show “not enabled / no data / access denied” distinctly. Do not copy personally identifiable participant data into tenant-wide portfolio analytics by default.
16. **Accounting queries and financial screens require bounded reads and truthful totals.** `src/app/api/accounting/route.ts:30-42` loads all orders, their payments/lines, payments, expenses and incomes for an edition. The finance view’s KPI source is bounded separately in the reviewed code (`src/components/maven/views/finance.tsx:35-67`), creating a risk that a displayed total reflects only a page-size subset while the API performs unbounded work. Replace with database-side aggregates plus cursor-paginated detail, and prove totals against unpaginated fixtures. Do not conflate booking/orders, captured funds, refunds and expenses.
17. **Performance and quality gates need field and workload evidence, not only a clean static check.** Define p75 Core Web Vitals separately for desktop and mobile; set query budgets and p95 API latency for high-volume dashboard, list, search and export paths; test realistic data volume and concurrency. The successful local health latency and static type/lint pass are not user-performance proof.
18. **Event state labels need a published lifecycle contract.** The live sample’s event end date had passed while its badge still said “Canlı”. Distinguish publication/access availability, registration close, operational live window, ended and archived. Permit a configured late-registration window when business rules require it, but make the state and dates explicit to staff and attendees; never infer archival solely from the date.

## 4. Sector-backed target decisions

These are implementation constraints, not endorsements of a particular vendor or a claim that the current app complies.

### 4.1 Tenant isolation and authorization

- **Authenticate identity, bind tenant context, then authorize the specific resource/action/scope.** AWS explicitly distinguishes tenant isolation from authentication and ordinary authorization: a correctly authenticated user can still reach another tenant unless tenant context is applied to every resource path. Carry the trusted Firma B tenant identity from server-authenticated membership, then resolve Work scope and action; never trust a request-supplied tenant/work/actor as the authorization source. [AWS SaaS Architecture Fundamentals — Tenant Isolation](https://docs.aws.amazon.com/whitepapers/latest/saas-architecture-fundamentals/tenant-isolation.html), [AWS SaaS Identity](https://docs.aws.amazon.com/whitepapers/latest/saas-architecture-fundamentals/saas-identity.html)
- **Deny by default; re-check each request at the protected resource; perform object-level checks for every identifier.** A `WorkId`, `editionId`, sponsor ID or participant ID in a URL is not proof of access. Enforce tenant, work, module, action and sensitive-field scope on every API and job. [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), [OWASP API1:2023 BOLA](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/)
- **Do not make tenant-per-customer databases, a pool/bridge/dedicated hybrid, or a policy microservice a day-one requirement.** The project’s pooled SQLite/PostgreSQL-compatible logical model can be the initial modular-monolith deployment if every query is tenant-aware and isolation tests cover every access path. Revisit physical isolation only when contractual/regulatory needs or measured workload justify the operations burden. AWS documents pool and silo as trade-offs, not a universal mandate. [AWS Prescriptive Guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/saas-multitenant-api-access-authorization/introduction.html)
- **Keep Firma A, Firma B and Work authority separate.** Firma A manages platform lifecycle and upper-bound module entitlements; Firma B administers its tenant, employees, departments, portfolio and its Work operations; each Work contains its own module activation, team, organizer/customer relationship and external grants. A client/organizer is not a tenant administrator. External capability grants must be narrow, work-bound, revocable and field-minimized.

### 4.2 Segregation of duties, approvals and audit

- **Use least privilege as the default and separate duties where risk requires it.** NIST AC-5 addresses separation of duties and AC-6 least privilege. Apply this to tenant/work role assignment, high-value manual collection/refund, external-submission approval and sensitive exports. Do not force two employees for every low-risk tenant operation; let Firma B policy set thresholds while preserving a trusted authenticated approver and audit trail. [NIST SP 800-53 Rev. 5](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final)
- **External sources remain proposals; internal authorized staff entries may be trusted according to configured policy.** Preserve source provenance and distinguish manual staff entry, public form, sponsor/organizer portal, XLS import and integration. This supports the agreed accountability boundary: Firma B owns the approval decision even when a partner can suggest a person or company.
- **Quota is not permission.** A sponsor’s guest allowance is a capacity entitlement, not authority to view all event participants, finance, or other sponsor agreements. Access scope and quota are separate authorization dimensions.

### 4.3 Modular extension without structural rewrites

- **Keep a modular monolith and make module contracts explicit.** One product-module manifest should feed catalog IDs, Firma A grants, Firma B activation, Work activation, dependencies, menu contributions, setup checklists, summary widgets, permissions, settings, forms/outcomes, external surfaces and acceptance tests. Current registries should be adapted by compatibility adapters and parity tests before any removal.
- **Treat module addition and template addition as additive, versioned changes.** A new form template should declare schema/version, audience/source, consent needs, review policy, supported outcomes and owning module. Consumers subscribe through explicit integration contracts or the transactional outbox; one module must not import another module’s internal database implementation. Existing records retain their schema version and work/tenant ownership.
- **Put each feature behind dependency and lifecycle checks.** For example, B2B scheduling can require sponsor/exhibitor identity and availability; a new form outcome can request a registration proposal but cannot directly create a trusted confirmed registration unless the approval policy permits it. Missing or disabled dependencies should fail closed and explain the requirement, not silently hide data or delete it.
- **Use architecture fitness tests to prevent drift:** UI/API/catalog count and IDs match; every module declares dependencies and permissions; no circular feature imports; every route maps to an owner module and scope; every module contributes tests; disabling a module preserves authorized historical read/export and safe reactivation.

### 4.4 PWA and responsive experience

- **A manifest’s `standalone` display mode and explicit navigation `scope` improve installed-app framing, but do not by themselves create a coherent native-like product.** Define separate app entry experiences and navigation for (1) public event/mobile information, (2) verified attendee’s personal entitlements, (3) email-verified B2B access, and (4) Firma B-granted partner portal. Keep the internal administrative console as its own work surface. An invite code or event code alone is not identity. [W3C Web Application Manifest](https://www.w3.org/TR/appmanifest/)
- **Offline is a data-classification rule.** Cache the static shell and explicitly public event assets only. Do not cache API responses containing PII, finance, role grants, portal tokens or private work data. Queue only specifically designed idempotent low-risk actions with visible pending/sync/conflict states; privileged approvals and money movement remain online and server-authorized.
- **Use WCAG 2.2 AA as the release target, not a visual claim.** Verify keyboard order, focus visibility, labelled controls, validation announcements, contrast, zoom/reflow and touch targets. WCAG 2.5.8 has a 24×24 CSS-pixel minimum target or spacing exception; 44×44 is a sensible product touch target for frequent mobile actions but must not be misrepresented as the WCAG minimum. [W3C WCAG 2.2 Understanding — Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum)
- **Set performance acceptance at p75, by device class:** LCP ≤2.5 s, INP ≤200 ms, CLS ≤0.1 for both mobile and desktop; add field RUM and identify slow API/DB contributors. These are web.dev’s current “good” Core Web Vitals thresholds, not a guarantee for every device. [web.dev — Web Vitals](https://web.dev/articles/vitals)

## 5. Revised implementation sequence and exit gates

This sequence adds gates to `00-MASTER-ROADMAP.md` and `07-IMPLEMENTATION-PHASES-AND-AGENT-PACKAGES.md`; it does not authorize implementation by itself.

1. **P0 — Freeze current feature inventory and evidence.** Capture the current route/module/schema/test inventory, backup hashes and DB parent-child integrity report. Explicitly label source-only versus live-verified claims. Protect all existing flows and records.
2. **P0 — Contain authorization and approval risks before new grants.** Fix/verify role-scope widening, caller-supplied approver identity, threshold-based two-person payment decision, sponsor agreement response scope, external form state ordering and cross-parent tenant/work validation. Exit only with real API-level positive and negative tests.
3. **P1 — Establish canonical identity and Work compatibility seam.** Introduce the Work identity adapter over the existing EventSeries/EventEdition graph; map customer/organizer, work type/profile, accountable owner and work modules without breaking historical edition URLs or APIs. Inventory/repair mismatched parent relationships before backfill.
4. **P1 — Establish one module catalog contract.** Resolve UI/API 27/26 discrepancy intentionally; make module ID and capability parity executable in CI. Only then introduce Firma A’s module grants, Firma B’s activation and Work activation as separate stored decisions. Preserve current module data when disabled.
5. **P2 — Add Firma A platform plane, then Firma B onboarding and home.** Firma A’s authorized operations surface grants maximum modules to a tenant; it does not expose source/deployment/secrets to Firma B. Firma B onboarding captures company profile, first accountable admin, departments, language and staff roles. The first authenticated screen is the current user’s permission-filtered Work portfolio and company settings—not an edition list.
6. **P2 — Add Work creation wizard and two-level navigation.** Group work types (events/meetings, exhibitions, travel/service work, custom) and progressively ask the appropriate questions. Work creation selects modules only from Firma B’s upper-bound grants and profile-compatible choices. After selecting a Work, land on its grouped summary and a scoped module rail with module subflows; preserve the legacy event wizard until parity is proven.
7. **P3 — Migrate modules in dependency order.** Start with core identity/portfolio, then forms/import/approval, registration/participation, finance, sponsorship/partner entitlements, event program/onsite/accommodation, communication, analytics and finally Floor Studio. Maintain compatibility adapters and cross-module outcome contracts; do not lift Floor Studio before the overall Work flow stabilizes.
8. **P4 — Build distinct external surfaces and PWA behavior.** Public event/mobile, verified personal, B2B, and partner experience are separately navigable and permission-shaped. Firma B grants/revokes external capabilities and field visibility. No external user sees the internal administration shell.
9. **P5 — Prove data migration, recovery and operations.** Use a disposable copy for migration and rollback; preserve source DB and SQLite WAL/SHM; prove restore with hashes and application-level validation; reconcile old/new counts and tenant/work parent chains. Do not run database tests against the user’s active local DB.
10. **P6 — Release gates and evidence.** Run production build, migrations on disposable clone, complete unit/API/E2E, role matrix, two-tenant negative tests, desktop/mobile UI, keyboard/axe/manual accessibility, install/standalone/offline PWA, load/performance tests and restore drill. Capture results and known gaps before marking a phase complete.

### Minimum acceptance matrix before the new architecture is called complete

| Area | Required proof |
|---|---|
| Firma A → Firma B | A cannot read/write a tenant outside platform scope; tenant entitlement is the upper bound; revoke blocks new work/feature access without destroying historical records. |
| Firma B → Work | Tenant staff can see only their assigned Works; work-only admin cannot gain tenant-wide powers; an authorized tenant admin can deliberately manage all Works. |
| Firma B vs Firma C | Same user/resource ID substitution, list/search/count/export, nested child references, files, background jobs and caches return no cross-tenant data. |
| Work modules | Not entitled → cannot activate; tenant inactive → cannot use; Work inactive → does not appear as operational module; historical data remains safely readable to authorized users. |
| External sources | Public/partner/import proposals remain pending; approval is session-attributed, auditable, idempotent and does not double-consume quota. |
| Sponsor/organizer | Agreement-scoped token sees only authorized agreement subresources and fields; quota is independent from permission; revocation takes effect promptly. |
| Finance | Order, captured payment, refund, income and expense reconcile; above-threshold manual transaction remains pending until a distinct authorized approver; no client-supplied actor is trusted. |
| Forms and portfolio | Canonical person/organization is reusable only within tenant policy; work participation is distinct; consent is purpose/channel-specific; template versions remain reproducible. |
| UI and PWA | Current-user portfolio, selected Work summary, second-level navigation, empty/denied/stale states, accessible keyboard/touch, mobile reflow, install scope and cache allowlist all pass. |
| Performance and recovery | p75 CWV goals by mobile/desktop, API/query budgets under realistic volume, migration/rollback rehearsal and verified restore all pass. |
